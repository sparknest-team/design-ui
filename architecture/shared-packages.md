# Cedar / Maple 基础工具边界

## 双端实现维护原则（2026-09-08）

所有需要跨端一致的组件和内部逻辑，优先采用自然同源复制：先修改并验证一端，再复制到另一端，直接在各库对应职责文件中调整产品前缀、包内导入和端侧标识；后续修改同步维护两份源码。

同源不以逐字相同为目标，也不要求新增 `platform.ts`、平台配置对象或仅为比较源码而存在的适配层。少量差异直接保留在两库各自的组件、composable、样式或 token 文件中；一致性门禁可以规范化已知前缀和 import 后比较。若桌面端与移动端的 DOM、手势、交互或视觉职责差异较大，则只统一公开契约、稳定的纯逻辑和生命周期原则，主体各自实现，并如实标记为“逻辑待同源”或“待适配”。

不采用两端 import 同一份核心实现、跨库组件引用、公共组件工厂或外部模板生成源码的方式。此约束不禁止各库内部工具复用，也不要求复制 Vue 等第三方依赖。

历史调研中的“共用”仅表示待同源对齐候选，不是已存在的共享实现，也不是未来抽公共运行时的计划。完成源码对齐及两端验证前，不能仅修改标签就声称已同源。此原则适用于所有跨端候选，不限于 Card / Affix / Badge。

`shared` / `use` 表示职责相似，不代表两端实现必须相同。桌面端和移动端在 DOM 行为、手势、响应式状态和组件约束上会持续分化，因此不抽取到外部公共包。

仓库内命名按所属产品保持清晰：

- Cedar：`@cedarjs/shared`、`@cedarjs/use`
- Maple：`@maplejs/maple-shared`、`@maplejs/maple-use`

两端只统一工程契约：目录职责、导出方式、测试门禁、SSR 安全和 API 命名。具体代码允许不同；只有某个纯函数经过长期验证确实完全一致时，才考虑复制规范或单独提案，不预先建立跨仓库运行时依赖。

### 文档工具不属于组件运行时

`@ui-foundation/ui-doc-preview` 是文档构建与展示工具，可以由 Cedar、Maple 文档站共同依赖。它不进入任一组件库的公开运行时，也不提供跨端组件实现，因此不违反组件“同源复制、独立维护”的约束。

公共包只包含预览外壳和 `DocPreviewSource` 协议；VuePress/Markdown 解析、路由、移动端 iframe、主题和 Playground 地址仍由各站点适配。Demo 源码继续放在各组件目录中。

## Card / Affix / Badge 的复制约束（2026-09-07）

这三个组件采用同一逻辑来源：先修改并验证一端，再复制到另一端，更改产品前缀、包内导入路径和安装入口。端侧标识直接留在各自对应文件中，不以抽取平台配置文件作为同源前提；渲染和行为没有实际端侧差异时不得另起实现。

两端保留独立源码、独立组件实例和独立响应式状态；不得互相导入组件、建立共享运行时单例，或以外部模板生成取代复制维护流程。可增加只读源码一致性检查，检查不修改或生成源码。
