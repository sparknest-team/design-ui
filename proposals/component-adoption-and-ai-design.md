# Cedar 与 Maple 组件使用与 AI 接入方案

版本 1.0 · 2026 年 11 月 14 日 · 产品与技术设计提案

## 1 目标与核心决策

本方案面向 Cedar Design Web 与 Maple Design Mobile 的产品、设计、文档和研发维护者，建立从能力发现、Demo 体验、标准实现获取到工程验证的完整使用路径。目标是让开发者和 AI 更容易选对组件、复用成熟实现，并能检查最终结果。

建议保留“特色与场景”作为对外展示入口，承载可操作的能力演示和业务组合方案；“组件”作为使用手册，保留最小运行示例、选型建议、交互约定与完整 API；另设“AI 与工具”承载 MCP、CLI、Skill 的接入和技术参考。场景页提供 AI 使用入口，组件页也可被 MCP 检索。三个入口共用内容资产，不各自维护一份代码。

这里的“推荐实现”指在明确适用条件和版本下，经过维护及验证的实现。不同平台、业务约束和性能要求可能对应不同方案，不能宣称存在适用于所有需求的唯一最佳写法。

## 2 现有基础与建设边界

Cedar 面向桌面应用，Maple 面向移动应用。共享治理源位于 design-ui，现有规范已经要求组件文档包含用途、何时不使用、示例、API、Token、键盘和可访问性说明，并要求预览和源码引用同一份 Demo 文件。

现有 configs/core-strengths.json 已登记能力标识、价值描述、演示步骤、关联组件及双端源码位置。例如 platform-contract、task-workbench、task-workflow 可作为首批内容基础。应扩展这个索引或从其生成场景清单，避免建立第二份独立维护的能力目录。

本提案设计信息架构和后续工具契约，不代表 MCP、Registry、安装命令或场景包已经发布。现有 Demo 需要按本文标准逐项核验后，才能升级为可分发方案。

## 3 官网信息架构

两站采用相同的一级导航顺序，桌面和移动内容按平台分别呈现。保留现有 VuePress 和 Maple CLI 路由，侧边菜单按所属栏目组织。下面列出公共结构；平台专属指南和组件保留在对应分组中。

```text
开始使用
  安装与快速开始
  平台选择与兼容性
  按需引入与跨端复用
  配置与约定 国际化
  样式与主题定制
  更新与迁移
    更新日志 Changelog
组件
  按功能分类的组件目录
  组件使用手册与基础示例
特色与场景
  全部能力与场景
  体系特色
    桌面与移动 表单 主题等能力演示
  业务场景与页面示例
AI 与工具
  AI 快速开始
  MCP 接入与故障排查
  CLI 与方案获取
  Skill 与团队规则
  工具和内容参考 LLM 文档
```

**更新与迁移归入“开始使用”**，其中提供 Changelog；不再占用一级导航。搜索入口当前暂时移除。需要查找组件时，通过分类目录进入。

“特色与场景”通过二级分类区分两类内容。特色回答“这套库有什么价值”，场景回答“我如何完成这个任务”。同一个 Demo 可以支持两种入口，但应指向同一详情页或同一源码资产。

顶部工具顺序统一为：阅读方向切换、GitHub 源码、主题、语言。语言与主题使用共用菜单；移动预览按空间展示必要工具，Demo 预览不重复展示完整文档导航。Cedar 和 Maple 的主题选项数量可以不同，控件样式与操作保持一致。

**当前状态**：四个一级入口和说明页面已在本地配置；MCP、场景 Registry、一键安装和官方 Skill 尚未发布，其页面说明现状，不提供虚构的接入命令。场景页的 AI 入口、筛选和分发能力仍属于后续建设项。以上以本地配置为准，线上发布状态需单独确认。

### 3.1 各类内容的职责

| 内容      | 回答的问题           | 应包含                                         | 主要后续动作             |
| --------- | -------------------- | ---------------------------------------------- | ------------------------ |
| 特色      | 为什么选择这套库     | 能力说明、可验证的演示、平台差异、适用限制     | 体验 Demo、进入相关场景  |
| 场景      | 如何完成一个任务     | 完整交互、推荐组合、源码、业务接入点、异常恢复 | 获取实现、交给 AI 适配   |
| 组件      | 单个组件如何正确使用 | 最小示例、选型、API、状态、可访问性、定制边界  | 复制用法、查看关联场景   |
| AI 与工具 | 如何配置和调用工具   | 安装配置、工具契约、版本规则、排错             | 完成接入、执行第一次检索 |

组件页不能退化为参数表。基础示例是学习和排错的必要入口；完整业务流程则在场景页说明，组件页只保留关联入口。MCP 使用案例不必全部挤进“特色与场景”：业务任务放场景，连接配置和工具说明放 AI 与工具，组件用法查询仍属于组件内容。

## 4 特色与场景页面设计

### 4.1 聚合页

首屏说明 Cedar 和 Maple 的平台定位，并允许按平台、任务、关联组件和发布状态筛选。卡片展示任务名称、用户可完成的动作、平台支持和“体验 Demo”。避免只有截图和宣传文字。

首批建议选择三个已有索引对应的内容：桌面与移动的统一公共约定、任务查询与状态联动、表单确认与失败恢复。每项先核实当前双端实现，再决定是否同时发布。后续按实际用户需求补充上传、排期或其他方案。

### 4.2 特色详情模板

1. 能力标题与一句价值说明。
2. 适用条件和支持的平台。
3. 可操作 Demo，并告诉用户先做什么、观察什么结果。
4. 关键机制和明确边界，例如模拟保存不等于提供业务后端。
5. 关联场景与组件手册。

### 4.3 场景详情模板

1. **任务与结果**：谁在什么情况下使用，完成后得到什么。
2. **适用与不适用条件**：数据规模、交互方式、平台和依赖条件。
3. **运行 Demo**：默认数据、重置、加载、空结果、错误和恢复入口。
4. **推荐实现说明**：为何采用这些组件，关键状态由谁持有。
5. **源码与获取方式**：可运行文件、依赖、匹配版本；未提供安装能力时只展示真实可用的源码获取入口。
6. **接入业务**：需要替换的数据读取、提交、鉴权和错误转换位置。
7. **AI 使用入口**：复制需求、复制上下文；工具发布后再提供已验证的客户端入口。
8. **验证与限制**：验证环境、已覆盖交互、未覆盖边界。
9. **相关内容**：组件手册、相邻方案、双端对应场景。

默认先显示 Demo 和必要操作说明，源码按需展开。验证记录保留在维护资料，公开页只呈现对使用者有意义的支持范围。所有演示失败都应可恢复，页面应提供回到初始状态的办法。

### 4.4 示例场景任务查询与状态联动

用户步骤：按部门查询 → 修改任务状态 → 按状态过滤 → 制造空结果 → 清空筛选并恢复。

Cedar 使用适合桌面的表格与就近操作；Maple 采用当前移动方案支持的触控布局。两端共用任务语义和业务数据契约，不要求布局逐像素一致，也不默认把桌面表格缩小就算移动适配。

用户可复制给 AI 的需求示例：

> 请基于任务查询与状态联动方案实现任务管理页，目标平台为 Maple。先检查当前项目的包版本和方案兼容性，使用方案中已支持的筛选和状态更新流程。把模拟读取与保存替换为我提供的接口，保留加载、空结果、失败恢复和重置行为。缺少接口契约时先保留清晰的数据适配接口，并说明待补字段。

这段需求用于表达任务，不应硬编码未确认的组件属性。AI 应从当前版本内容获取真实 API。

## 5 组件页设计

组件页按“用途与选型 → 最小示例 → 功能示例 → 交互约定 → API 与类型 → 样式变量 → 可访问性 → 关联场景”组织，并保持既有规范要求的完整性。具体锚点可沿用当前站点约定。

最小示例负责让用户第一次使用成功，功能示例解释单项能力，场景入口连接完整任务。例如 Form 组件页解释校验和提交行为，并链接“表单确认与失败恢复”；不再把完整业务流程复制成另一份源码。

组件级 AI 入口可支持“解释这个组件”“根据当前版本生成最小用法”“查找相关场景”。它们属于 MCP 的合理使用范围，因此 MCP 内容来源不能只包含场景库。

## 6 内容资产与双端策略

### 6.1 统一资产关系

```text
组件公开契约与类型 ──→ 组件手册与 API 索引
可执行 Demo 源码 ───→ 页面预览与源码展示
能力和场景元数据 ───→ 官网目录与 Registry 索引
上述版本化资产 ─────→ MCP 查询与 Skill 引用
验证结果 ──────────→ 发布门禁与支持范围
```

官网、MCP 和 CLI 应消费同一版本的内容快照。文档展示的代码与工具获取的代码必须一致。不要把 Markdown 内嵌代码、预览源码和 MCP 返回片段分别手工维护。

### 6.2 场景元数据建议

下列是待实现的数据模型，字段名称可按现有索引演进。

| 字段                      | 含义                                      |
| ------------------------- | ----------------------------------------- |
| id 与 revision            | 稳定任务标识与方案修订版本                |
| kind                      | feature 或 scenario                       |
| title 与 summary          | 可本地化名称与任务说明                    |
| tags 与 components        | 需求检索词与关联组件                      |
| platforms                 | Cedar 和 Maple 的独立支持状态、入口与源码 |
| compatibility             | 各端包版本范围、Vue 条件及依赖约束        |
| files 与 dependencies     | 真实文件、依赖及内容校验值                |
| states 与 extensionPoints | 已实现状态和业务替换位置                  |
| status                    | experimental、stable、deprecated          |
| validation                | 对应版本的验证项目、环境和时间            |
| docs 与 related           | 组件、场景和指南链接                      |

共享 id 表达同一任务，平台变体保留独立实现、版本范围和验证状态。两库独立发布，不要求版本号相等。缺少某端实现时明确标记，不通过替换组件前缀宣称支持。

## 7 MCP 与 Skill 设计

### 7.1 MCP 的职责

MCP 提供可查询的真实资产与兼容信息。建议第一阶段只做只读查询，方案写入项目由显式 CLI 操作完成，便于预览文件差异和处理冲突。MCP 本身不保证业务正确性，也不自动把一次 Demo 验证推广为所有使用方式都可用。

以下工具名称为建议契约，尚非现有公开 API：

| 建议工具          | 输入重点                        | 输出重点                                     |
| ----------------- | ------------------------------- | -------------------------------------------- |
| search_components | 任务、平台、已安装版本、语言    | 候选组件、适用条件、匹配版本                 |
| get_component     | 组件、平台、版本                | 真实 API、最小示例、限制、关联场景           |
| search_scenarios  | 需求、平台、版本、交互约束      | 候选方案、匹配原因、不满足的条件             |
| get_scenario      | 场景 id、平台、revision、包版本 | 说明、文件清单、源码、依赖、扩展点和验证范围 |
| get_setup_guide   | 平台、构建环境、版本            | 安装、主题、语言与引入指导                   |

所有结果应带来源、内容版本和兼容状态。不匹配版本时返回明确的不兼容信息和可选方案，不能静默返回最新版。查询较大内容时先返回摘要与文件索引，再按需读取，避免一次灌入所有 API。

### 7.2 Skill 的职责

Skill 描述任务流程：检查项目平台和依赖 → 检索方案 → 判断适用性 → 阅读源码与扩展点 → 获取并适配 → 运行工程检查 → 验证实际交互。

Skill 引用版本化资料，不抄录整套 API；避免随版本更新迅速过期。无法获得兼容方案时，AI 应基于真实组件契约组合并说明自定义部分，不能冒充官方标准实现。

### 7.3 场景页的 AI 入口

初期提供“复制需求”和“复制方案上下文”，包含场景 id、目标平台、文档地址、revision 和推荐验证步骤。不要把“复制提示词”命名为“一键完成”。

MCP 发布后，在场景页显示所需配置的状态说明，并链接 AI 快速开始。客户端深链和一键安装仅在有真实协议支持并经过验证后提供；对未接入 MCP 的用户，源码浏览和手动接入路径仍应完整。

## 8 Registry 与 CLI 分发设计

Registry 是版本化方案目录，可以先采用内部 JSON 契约；是否兼容 shadcn Registry 需独立核实 Vue 文件、依赖和安装流程，不能把其 React 生态方案视为可直接套用的 Vue 运行方案。

CLI 的最小能力包括查看方案、预览文件与依赖变化、安装指定修订、检测现有文件冲突。默认不覆盖用户已有文件，输出改动清单。安装前核对目标包版本，安装后记录来源和 revision。

组件作为 npm 依赖管理，业务场景初期以可编辑源码分发。只有多个场景都需要且契约稳定的通用行为，才考虑抽成公共组件或 composable，避免每个 Demo 都变成新组件。

## 9 验证与发布门禁

场景进入 stable 前至少满足以下条件：

- 文件与依赖完整，能在声明支持的环境中独立运行；公开命令必须真实可执行。
- 类型、构建和现有文档门禁通过；文档、预览、源码展示引用一致。
- 正常流程、空结果、失败、恢复与重置行为经过验证；无适用状态时说明原因。
- Cedar 检查键盘和焦点交互；Maple 检查触控、滚动、输入和目标视口。桌面窄窗口不能替代真机结论。
- 主题、语言和浮层作用域按场景声明核验，公开支持范围与证据相符。
- MCP 返回的版本、文件校验值与该发布快照一致，过期内容不会被当作当前 API。

AI 接入需要额外建立代表性任务集：组件选型、获取完整场景、已有项目接入、版本不兼容、错误 API 纠正。每个任务明确预期资产和成功条件，区分检索正确与最终任务完成。

建议跟踪首次运行成功率、完成任务需要的人工修改次数、错误 API 比例、场景复用率和版本不匹配率。先记录基线再制定目标，不以未经测量的百分比承诺效果。

## 10 分阶段实施

| 阶段                | 交付物                                         | 完成条件                                |
| ------------------- | ---------------------------------------------- | --------------------------------------- |
| 第一阶段 内容梳理   | 三类入口边界、首批三个场景、双端支持清单       | Demo 与源码一致，适用条件和组件链接完整 |
| 第二阶段 资产结构化 | 扩展现有能力索引、版本快照、文件清单、内容校验 | 官网和查询索引可从同一资产生成          |
| 第三阶段 AI 查询    | 只读 MCP、AI 接入指南、任务 Skill              | 代表性任务验证通过，版本冲突有明确反馈  |
| 第四阶段 方案分发   | CLI 预览与安装、依赖检查、冲突检测             | 新项目和已有项目的获取流程可复现        |
| 第五阶段 持续治理   | 发布门禁、废弃策略、使用反馈与任务评估         | 新方案可重复发布，旧方案可追溯和迁移    |

先把已有 Demo 升级为完整且可靠的场景资产，再接工具。第一阶段即可改善官网使用体验，不必等待完整 MCP 与 CLI。

## 11 内容维护责任

组件维护者负责 API、最小示例和交互边界；场景维护者负责业务组合、扩展点和恢复流程；平台维护者分别确认 Cedar 与 Maple 的适配及验证；工具维护者负责索引、版本解析和分发一致性。一次改动可能涉及多个角色，可由同一人承担，但责任不能被工具生成过程隐去。

组件 API 或行为变化时，应反查关联场景、工具索引和兼容范围；场景变化不自动要求两库同步发版。中英文内容遵循现有文档约定，缺失译文明确呈现状态。

## 12 设计依据

项目依据：design-ui/standards/documentation.md、design-ui/standards/demo-design.md、design-ui/configs/core-strengths.json、design-ui/README.md、maple/README.md。

外部参考用于理解成熟工具分工，实施前需核对具体版本和协议：

- [shadcn Registry](https://ui.shadcn.com/docs/registry/getting-started) 与 [MCP](https://ui.shadcn.com/docs/mcp)：参考结构化资产检索与分发。
- [MUI MCP](https://mui.com/material-ui/getting-started/mcp/)：参考官方组件资料向 AI 的提供方式。
- [Atlassian Design System 工具](https://atlassian.design/tools)：参考设计系统规则与工程工具协同。

这些工具各自解决内容获取、代码分发或规则检查的一部分。本方案将它们的职责结合到 Cedar 与 Maple 的 Vue 组件和现有双端文档体系中。
